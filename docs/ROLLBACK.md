# 回滚流程

## 1. 触发条件

- 首页、登录、后台或核心业务路径不可用；
- 智能体或工作流持续报错；
- 资产、算力、订单或历史记录出现数据不一致；
- 服务持续 5xx、无法启动或出现明显安全回归。

## 2. 代码与静态文件回滚

1. 确认故障首次出现的发布版本和时间。
2. 停止继续发布，保留故障日志和当前候选文件副本。
3. 使用发布前创建的精确文件备份，只恢复本次发布实际覆盖的文件。
4. 恢复上一版 `server/` 与 `dist/`，不要覆盖 `/opt/usun/.env` 或 `/opt/usun-data`。
5. 重启 `usun.service`，重复发布后的核心烟雾测试。

优先使用上一版已验证候选或文件备份，不使用 `git reset --hard` 直接处理生产目录。

## 3. 数据边界

不要通过 Git 回滚数据库。数据库、上传文件、知识库文件和向量数据不属于代码候选包。

只有在明确存在数据迁移故障、已保留事故现场副本并有对应恢复方案时，才允许进入数据恢复流程。数据恢复应使用数据库或 COS 备份，并在恢复前再次核对目标时间点和影响范围。

## 4. 回滚完成记录

记录故障版本、回滚版本、受影响路径、数据是否受影响、验证结果和后续修复责任。回滚成功后，不得在没有新候选回归证据的情况下再次发布同一故障版本。
